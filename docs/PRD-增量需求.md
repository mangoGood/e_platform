## 0. 现状勘察结论（与需求方认知的差异，请先对齐）

编写本 PRD 前已实地核查代码，以下 5 条与「项目现状」描述存在出入，**直接影响工作量评估**，请架构师与需求方优先确认：

| # | 认知 | 代码实际情况 | 影响 |
| --- | --- | --- | --- |
| C1 | 「一键启停脚本已有」 | `start.sh` 为 **0 字节空文件**；`stop.sh` 可用但仅停 Java 进程，且明确提示"Docker 容器请自行 `docker-compose down`" | 启动脚本需从零构建；停止脚本需补齐 Docker 编排 |
| C2 | 「已实现单层商品评价」 | 仅有 `Review` 实体 / `ReviewMapper` / `ReviewService` / `ReviewController`（3 个接口）。**`addReview()` 无任何购买校验**——任意登录用户可对任意商品刷评论 | 是安全缺陷而非可用功能，L1 层需重做而非扩展 |
| C3 | 「有 JWT 鉴权」 | 网关 `GatewayController` 是 **Spring MVC + RestTemplate 手写代理**（非 Spring Cloud Gateway）。鉴权仅"校验 Token 是否可解析"，无角色校验、无失效机制 | IAM 需在现有代理层上重构 |
| C4 | 网关身份传递安全 | `proxyRequest()` 先**全量透传客户端 Header**（含客户端伪造的 `X-User-Id`），再由 `extractUserFromToken()` 覆盖。Token 无 `userId` claim 或走公开路径时，**伪造头可穿透到下游服务** | **高危越权漏洞**，P0 必修 |
| C5 | 微服务信任模型 | `product/order/user` 服务直接 `@RequestHeader("X-User-Id")` 取值即信任。服务端口 8085-8089 若可直连即可完全绕过网关冒充任意用户 | 需建立"网关签名 + 服务侧校验"信任链 |
| C6 | Android 评论能力 | 64 个 kt 文件中**无任何 review/comment 相关代码** | 三级评论在 App 端是纯新增，非改造 |

> **结论**：本次不是"加个评论功能"，而是「**补齐鉴权安全底座 + 新建三级评论体系 + 建立并发保护 + 视觉升级 + 修复交付脚本**」五件事。

## 1. 产品目标

本次增量围绕 3 个正交目标：

| 目标 | 描述 | 衡量口径 |
| --- | --- | --- |
| **G1 可信** | 从"能登录"升级为**完整 IAM**：RBAC 角色权限模型、细粒度接口鉴权、Token 全生命周期管理、越权防护 | 越权测试用例（伪造 Header / 跨用户改商品 / 未购买评论 / 登出后复用 Token）**100% 拦截** |
| **G2 可交互** | 建立**三级评论体系**，让交易后的商品页从"单向展示"变为"买家—卖家—潜在买家"三方对话场域 | 商品详情页可完成 L1 评价 → L2 卖家回复 → L3 第三方追问 完整链路，权限矩阵零漏判 |
| **G3 可用可看** | 支撑**多客户端并发**（超阈值排队而非拒绝）+ **视觉升级**至现代电商观感，并修复一键启停交付链路 | 50 并发下单不超卖、排队有位次反馈；`./start.sh` 一条命令拉起全栈；APK 可安装运行 |

**非目标（本次明确不做）**：支付渠道对接、物流对接、商品 SKU 多规格、优惠券/营销、店铺装修、消息推送、竞品与市场分析。

## 2. 用户故事

### 买家（Buyer）
- **US-B1**：作为买家，我希望**只有在收到货后**才能对商品评价（打分 + 文字 + 图片），这样评价区才可信。
- **US-B2**：作为买家，我希望能看到卖家对我评价的回复，感觉被重视；也能看到别人对我评价的追问并回答他。
- **US-B3**：作为买家，我希望下单高峰期不是直接报错，而是告诉我"前方还有 N 人、预计 X 秒"，让我决定等还是走。
- **US-B4**：作为买家，我希望登出后我的 Token 立即失效，即使被人截获也无法冒用。

### 卖家（Seller）
- **US-S1**：作为卖家，我希望能回复买家对**我自己商品**的评价，处理差评、维护口碑。
- **US-S2**：作为卖家，我希望**无法**回复别人家商品的评价，也无法删除买家的差评（只能举报），保证平台公正。
- **US-S3**：作为卖家，我希望在卖家中心看到"待回复评价"数量，不遗漏客诉。
- **US-S4**：作为卖家，我希望即使有人拿到我的用户名，也无法通过伪造请求头修改我的商品。

### 游客 / 第三方登录用户（Guest / Other User）
- **US-G1**：作为游客（未登录），我希望能**浏览**商品和全部三级评论内容，但需要登录才能参与互动。
- **US-G2**：作为一个还没买的登录用户，我希望能在某条真实评价下**追问**（"电池续航到底怎么样？"），由评价者或卖家解答，帮我决策。
- **US-G3**：作为潜在买家，我希望**不能**伪造"已购买"身份去发评价，保证我看到的评价都是真买家写的。

### 运维 / 开发者（Ops）
- **US-O1**：作为运维，我希望 `./start.sh` 一条命令按依赖顺序拉起 Docker 基建 + 5 个微服务 + 前端，并做健康检查。
- **US-O2**：作为运维，我希望 `./stop.sh` 能完整停掉全部服务**含 Docker 容器**，且可选保留数据卷。
- **US-O3**：作为运维，我希望 Redis 使用官方 `docker.1ms.run/redis:7` 镜像，且切换后配置不残留 bitnami 专有变量。
- **US-O4**：作为运维，我希望能通过配置调整排队阈值，而不用改代码重新打包。

## 4. 权限矩阵

### 4.1 三级评论权限矩阵

角色定义：
- **游客**：未登录
- **普通登录用户**：已登录，未购买该商品（含其他卖家）
- **已购买家**：对该商品存在状态=3（已完成）的订单
- **商品卖家**：该商品 `seller_id` 本人
- **其他卖家**：已登录卖家，但非该商品所有者
- **管理员**：`ROLE_ADMIN`

| 操作 | 游客 | 普通登录用户 | 已购买家 | 商品卖家 | 其他卖家 | 管理员 |
| --- | :---: | :---: | :---: | :---: | :---: | :---: |

| 编辑自己的 L1 | ❌ | ❌ | ✅ 24h 内 | ❌ | ❌ | ❌ |

| 隐藏/恢复任意评论 | ❌ | ❌ | ❌ | ❌ | ❌ | ✅ |

**边界规则（逐条明确，避免实现期歧义）**：

1. **未购买者不能发 L1** —— 返回 403，文案「购买并确认收货后才能评价」。
2. **订单状态必须为已完成（status=3）** —— 待收货状态不可评价，避免刷单。
3. **卖家不能重复回复** —— 同一条 L1 已存在未删除的 L2 时，再次提交返回 409，前端应改为"编辑"入口。
4. **L2 删除后可重新回复** —— 逻辑删除后允许再发一条。
5. **L3 不嵌套** —— 所有 L3 的 `root_id` 均指向 L1，`parent_id` 也指向 L1；回复具体某人仅通过 `reply_to_user_id` 渲染 `@昵称`，**DB 层不产生第 4 层**。
6. **卖家可以在自己商品的评价下发 L3** —— 用于补充说明（与 L2 正式回复区分），允许多条。
7. **级联可见性** —— L1 被删除或 `status=0` 时，其下全部 L2/L3 在查询层直接过滤，不返回。
8. **匿名与脱敏** —— 所有层级展示脱敏用户名；L2 额外展示「卖家」官方标识。
9. **自评防护** —— 卖家不能对自己的商品下单后发 L1（下单环节即应拦截；若已存在历史数据，评价接口二次校验 `seller_id != userId`）。

## 6. 排队机制产品定义

### 6.1 设计原则
**"宁排队，不拒绝"** —— 高峰期用户看到的是"你在队列中"，而不是报错页。同时**只保护真正稀缺的写操作**，浏览体验绝不降级。

### 6.2 分层策略

| 层级 | 接口范围 | 策略 |
| --- | --- | --- |
| **直接放行** | 所有 GET 浏览：商品列表/详情、分类、评论查询、静态资源 | 不排队、不限流（仅保留基础防刷） |
| **限流不排队** | 登录、注册、发评论、加购物车 | 令牌桶限流；超限返回 **429** + "操作过于频繁，请稍后再试" |
| **排队保护** | `POST /api/order/create`、`PUT /api/product/{id}/deduct` | 并发许可 + 等待队列（核心机制） |

### 6.3 阈值定义（全部可配置，走环境变量 / 配置中心）

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `queue.permits` | **50** | 同时处理的最大并发数 |
| `queue.max-length` | **500** | 等待队列最大长度 |
| `queue.wait-timeout` | **60s** | 单用户最长等待，超时自动放弃 |
| `queue.permit-ttl` | **30s** | 许可持有超时，防止异常导致名额泄漏 |
| `queue.poll-interval` | **2s** | 前端轮询位次的间隔 |

### 6.4 状态机与响应约定

| 场景 | HTTP | 响应体 | 用户感知 |
| --- | --- | --- | --- |
| 有空闲许可 | 200 | 正常业务结果 | 无感知，直接成功 |
| 无许可，入队成功 | **202** | `{queueToken, position, estimatedWaitSeconds, totalInQueue}` | 弹排队遮罩：「前方还有 **N** 人，预计 **X** 秒」 |
| 轮询中，仍在排队 | 202 | 同上（position 递减） | 位次实时刷新，进度条前进 |
| 轮到该用户 | 200 | 业务结果 | 遮罩自动关闭，**自动继续原请求**，无需重新点击 |
| 队列已满 | **503** | `{code:503, message:"当前抢购人数过多，请稍后再试"}` | 友好提示页 + "重试"按钮 |
| 等待超时（>60s） | **408** | `{code:408, message:"等待超时，请重新提交"}` | 提示并恢复到可重试状态 |
| 用户主动放弃 | 200 | 释放队列名额 | 遮罩关闭，回到原页面，**不产生订单** |

`estimatedWaitSeconds` 估算口径：`position / permits × 平均处理耗时`（平均耗时取近 1 分钟滑动窗口，冷启动默认 500ms）。

### 6.5 用户体验细则
1. 排队遮罩**不可被误关**（点击遮罩层无效），只能通过"放弃排队"按钮退出，防止用户误以为失败而重复下单。
2. 位次**只减不增**（即使真实位次波动，展示值取历史最小值），避免"越排越后"的挫败感。
3. 等待超过 **20 秒**时追加安抚文案：「正在为你保留名额，请勿关闭页面」。
4. 页面刷新/重进时凭 `queueToken`（存 sessionStorage）**恢复排队状态**，不丢名额。
5. 同一用户对同一商品**重复提交自动去重**，返回已有 `queueToken`，不占用两个名额。

### 6.6 降级策略
- **Redis 不可用** → 降级为单机 JVM 信号量，保证下单不中断，日志告警。
- **队列组件整体异常** → 熔断为"直接放行 + 数据库乐观锁兜底"，宁可慢也不阻断交易；库存扣减必须依赖 DB 层 `stock >= quantity` 条件更新，**排队机制绝不能是防超卖的唯一手段**。
- **超卖硬保障**：`UPDATE product SET stock = stock - #{qty} WHERE id = #{id} AND stock >= #{qty}`，受影响行数为 0 即失败回滚。

### 2.2 标杆方案详述

> 每家标杆逐一展开（至少 3 家必须有详述）；每段要区分「已核实的事实」与「推断/假设」。

#### 2.2.1 B1 - Shopify（Admin API + Shop 评价体系）

| 维度 | 内容 | 置信度 |
| --- | --- | --- |
| 产品定位 | 面向中小到企业级商家的托管式电商 SaaS，以 Admin API / Storefront API 对外开放平台能力 | 已核实 |
| 目标用户 | 独立站商家、品牌方、以及围绕其构建应用的第三方开发者（App 生态） | 已核实 |
| 核心能力 | ① 标准商品评价对象；② 员工/应用双轨细粒度权限；③ 平台级 API 配额与过载保护；④ 订单—评价强关联 | 已核实 |
| 架构特点 | 评价以 **metaobject** 建模，字段含 `rating` / `body` / `order`（订单引用）/ `app_verification_status`（取值 `verified_buyer`）/ `merchant_reply` / `merchant_replied_at`。**关键事实：商家回复（L2 语义）是评价对象上的两个平铺字段，而非独立的子节点记录**——标准定义中不存在第三层结构 | 已核实（字段清单见 SR-02） |
| 部署形态 | SaaS（多租户托管，不提供私有化） | 已核实 |
| 集成方式 | GraphQL Admin API（主）+ REST Admin API；`X-Shopify-Access-Token` 头认证；Webhook 订阅 `METAOBJECTS_CREATE/UPDATE/DELETE` 生命周期事件 | 已核实 |
| 定价模式 | 订阅分层，且**配额与套餐直接绑定**：GraphQL Admin API 为 Standard 100 点/秒、Advanced 200 点/秒、Plus 1000 点/秒、Enterprise 2000 点/秒 | 已核实（SR-06） |
| 优势 | ① 权限模型可直接对照：`StaffMemberPermission` 枚举约 30 项（ORDERS / PRODUCTS / CUSTOMERS / DRAFT_ORDERS / EDIT_ORDERS / DELETE_CUSTOMERS 等），且 Admin API scope 成对出现（`read_products` / `write_products`），后台权限项之间有**依赖自动勾选**机制；② 过载保护采用漏桶算法，响应体 `extensions.cost.throttleStatus` 回传 `maximumAvailable` / `currentlyAvailable` / `restoreRate`，使客户端可自适应；③ **Checkout 级节流超限返回 `200 Throttled`，官方明确建议「实现请求队列 + 指数退避」** ——即头部 SaaS 在结算这一关键路径上主张「排队重试」而非「直接拒绝」 | 综合归纳（各分项均已核实，见 SR-02/04/05/06） |
| 局限 | ① 闭源 SaaS，代码不可复用，仅能借鉴模型；② 数据托管于境外，与本项目单机私有化诉求相悖；③ 标准评价对象无第三层（第三方追问）语义，`merchant_reply` 为单条文本字段，无法承载多条 L2；④ Shop 渠道商家回复上限 1000 字符且**发布前可能被审核**，属平台治理策略而非通用工程范式 | 已核实 + 推断 |
| 对本项目的参考价值 | ① 佐证「购后评价必须绑定订单 + 买家身份核验」（`order` 引用 + `verified_buyer`），直击 K2「无购买校验、任意登录用户可刷评论」缺陷；② 佐证「细粒度权限应按资源 × 动作成对建模」，可映射到本项目权限矩阵；③ 佐证「排队优于拒绝」（Checkout throttle 官方建议）；④ 反向提示：L2 平铺是头部 SaaS 在两层场景下的选择，但本项目需 L3，故不能照搬平铺 | 推断 |

#### 2.2.2 B2 - Cloudflare Waiting Room

| 维度 | 内容 | 置信度 |
| --- | --- | --- |
| 产品定位 | 部署在 CDN 边缘的虚拟等候室，在流量超过站点承载力时对访客排队，保护源站不被击穿 | 已核实 |
| 目标用户 | 有秒杀 / 抢购 / 票务 / 限量发售等瞬时峰值场景的网站运营方 | 已核实 |
| 核心能力 | 流量洪峰检测、FIFO 排队、等待页托管、动态放行 | 已核实 |
| 架构特点 | 构建于 Cloudflare Workers 之上；以 Cookie 标识访客会话，保证同一访客在队列中的位置稳定；按「总活跃用户数」与「每分钟新用户数」双阈值判定是否启动排队；根据实际出站速率动态调节入场速率 | 已核实 |
| 部署形态 | SaaS（流量必须经由 Cloudflare 边缘网络） | 已核实 |
| 集成方式 | 在 Cloudflare 控制台按 Host / Path 配置规则，对应用代码无侵入 | 已核实 |
| 定价模式 | 随 Business / Enterprise 套餐提供 | 已核实 |
| 优势 | ① 将「排队」抽象为独立于业务的基础设施能力，业务代码零改造；② 用户侧体验完整（等待页 + 位置稳定 + 自动放行），是「排队而非拒绝」的完整 UX 范式 | 综合归纳 |
| 局限 | ① 强依赖公网入口与边缘网络接入；② 保护粒度是「站点/路径级流量」，无法表达「某商品剩余库存 N 件」这类**业务资源级**并发约束；③ 流量需经境外节点 | 已核实 + 推断 |
| 对本项目的参考价值 | 仅在**交互契约层**可借鉴：排队应回传「排队中」的独立状态与预计位置/等待时间，前端据此渲染遮罩并轮询——正对应 ARCH 规划的 HTTP 202 + 2s 轮询 + 自动继续。**基础设施层不可借鉴**：e_platform 为 localhost 单机 Docker Compose，无公网入口，且需要的是库存级而非流量级排队 | 推断 |

**跨标杆补充事实（技术禁区）**：Spring Cloud Gateway 官方文档明确其构建于 **Spring WebFlux（响应式、非阻塞）** 之上，与 Spring MVC（servlet）栈**不兼容**；官方给出的处置方式是设置 `spring.main.web-application-type=reactive` 或移除 `spring-boot-starter-web` 依赖（SR-09）。e_platform 现有服务均为 servlet 栈，此事实构成 Q1/Q5 的硬约束。

**框架维护状态事实**：Spring Boot 2.7 首个版本发布于 2022-05，**开源支持已于 2023-06 结束**，此后仅通过商业订阅提供企业支持（至 2029-06）（SR-10）。结合 K22（2.7.18 官方支持 Java 8–19）与 K6（系统仅有 JDK 24.0.1 / 21.0.9 / 1.8.0_472，无 17），当前「2.7.18 + JDK 21」组合处于官方支持矩阵之外。

**并发原语事实**：Redisson 提供 `RPermitExpirableSemaphore`，其每个许可具有唯一 ID 且可设置租约时间（lease time），**持有者崩溃后许可自动释放**，避免永久泄漏；同时提供 `RSemaphore`、`RCountDownLatch` 等分布式同步器（SR-11）。

**安全基线事实**：OWASP API Security Top 10（2023）将 **API1 BOLA（对象级授权失效）**、**API2 认证失效**、**API3 BOPLA（对象属性级授权失效）**、**API5 BFLA（功能级授权失效）**、**API6 业务流无限制访问** 列为首要风险（SR-12）。K3（无角色校验）对应 API5，K4（Header 伪造穿透）与 K5（下游直接信任 `X-User-Id`）对应 API1 + API2，K2（任意登录用户可刷评论）对应 API1 + API6。

**移动端交付事实**：Android 应用必须签名方可安装；debug keystore 为公开共享凭据，不可用于发布；自 Android 7.0 起引入 V2 签名方案（后续有 V3），可用 `apksigner verify --verbose` 校验签名方案生效情况；release keystore 一旦丢失将无法为同一应用发布更新，须离线备份（SR-22）。此事实直接支撑 K8「两 App 无 `signingConfigs` 产出 unsigned APK 无法安装」。

### 3.2 评分结论

> 基于 §3.1 加权总分，形成分层结论。每层结论必须引用得分作为依据。
>
> **分档阈值**：加权总分 ≥ 4.00 为优先借鉴；3.00 ~ 3.99 为部分借鉴；低于 3.00 为不借鉴（否决）。

- **优先借鉴**：
  - **B4 macrozheng/mall + mall-swarm** — 适用度评分：**4.80**（六家最高）。理由：场景契合度 5/5（Java 电商全域覆盖①⑤）+ 集成难度 5/5（`dev-v2` 分支为 Spring Boot 2.7 + MyBatis + MySQL + Redis，与本项目同源，是六家中**唯一可做代码级对照**的对象）+ 成本 5/5（Apache-2.0）+ 合规可控性 5/5（完全自托管）。技术成熟度仅 4/5 系其定位为学习型参考实现而非生产验证的商业系统，故须限定为「对照参考」。
  - **B6 Discourse** — 适用度评分：**4.30**。理由：技术成熟度 5/5（长期生产验证）+ 合规可控性 5/5 + 成本 5/5；场景契合度 4/5 系其精准命中诉求②的核心难点——`posts.reply_to_post_number` 单表自关联 + 递归 CTE 已在生产中支撑任意深度嵌套回复，且「主楼与回复共表」与本项目 K25 既定的「`Comment` 与 `Review` 共表」方向天然一致。集成难度 3/5 反映其 Ruby/PostgreSQL 栈异构、代码不可复用，仅数据模型可迁移。

- **部分借鉴**：
  - **B5 Apache APISIX** — 适用度评分：**3.70**。借鉴点：`jwt-auth` 对签名算法（HS256/RS256/ES256）与**密钥外置**（环境变量 / Vault）的处理范式，可指导本项目 `JWT_SECRET` / `GATEWAY_SIGN_SECRET` / `INTERNAL_TOKEN` 的管理方式（呼应 K19 由 `env.sh` 用 `openssl rand` 随机生成）。不借鉴的部分：**不引入 APISIX 运行时**。理由：集成难度仅 2/5——引入将使单机 Compose 栈额外增加 OpenResty 与 etcd 两个中间件，与 K1「一键启停」的简化目标直接冲突；且现有网关承载的 `INTERNAL_DENY` 403 拦截（K7）、`X-User-Id` 注入、HeaderSanitizer 前缀黑名单（K4）、HMAC 签名生成（K5）需整体改写为 Lua 插件，改造面远超收益。
  - **B1 Shopify** — 适用度评分：**3.50**。借鉴点：① 评价对象强绑定订单与买家核验（`order` 引用 + `app_verification_status: verified_buyer`），直接对治 K2「无购买校验、任意登录用户可刷评论」；② 权限按「资源 × 动作」成对建模（`read_*` / `write_*`）+ 权限依赖自动勾选，可映射为本项目权限矩阵设计原则；③ 过载保护向调用方回传配额状态（`throttleStatus` 三元组），以及 **Checkout 节流官方建议「请求队列 + 指数退避」**，为诉求③「排队而非拒绝」提供头部 SaaS 佐证。不借鉴的部分：不采购、不迁移、不照搬其数据模型。理由：集成难度 2/5（闭源 SaaS，GraphQL/metaobject 与 MySQL+MyBatis 差异过大）、成本 2/5（订阅制且配额绑定套餐）、合规可控性 2/5（无私有化、数据托管境外）。**特别提示**：其 `merchant_reply` 为平铺字段而非独立节点，仅适用于两层场景，本项目需 L3 第三方追问，此点**不可照搬**。
  - **B3 Saleor** — 适用度评分：**3.20**。借鉴点：验证「具备完整电商域能力的系统，其官方标准分发形态可以就是 `docker compose up`」，并提供 api / worker / db / cache / dashboard 的服务切分惯例，为 K1 补齐 `start.sh` 提供形态参照。不借鉴的部分：技术栈与前端方案整体不采纳。理由：场景契合度仅 2/5——Python/Django + GraphQL + PostgreSQL + React 与本项目全面异构，代码零可复用，且评论体系非其强项、Dashboard 对 Vue3 前台无迁移价值。

- **不借鉴（否决）**：
  - **B2 Cloudflare Waiting Room** — 评分：**2.90**（六家最低，且为唯一低于 3.00 分档线者）。否决理由：① **前置条件不成立**——集成难度 2/5，该能力强依赖公网入口与 Cloudflare 边缘网络接入，而 e_platform 为 localhost 单机 Docker Compose 部署，不具备接入条件；② **保护粒度错配**——场景契合度 3/5，其排队作用于「站点 / 路径级流量」，无法表达「某商品剩余库存 N 件」这类业务资源级并发约束，而诉求③要求保护的正是下单扣库存路径；③ 合规可控性 2/5（流量需经境外节点）+ 成本 2/5（Business/Enterprise 套餐）。
  - **保留说明**：否决的是**其作为基础设施方案被引入**；其「排队而非拒绝」的用户侧交互契约（等待状态独立回传 + 位置稳定 + 自动放行）仍作为设计参照写入 §4.1，此为设计模式引用，不改变本条否决结论。

### 4.3 技术栈参考建议

| 技术层 | 推荐方案 | 替代方案 | 选择理由 |
| --- | --- | --- | --- |
| API 网关 | 沿用现有手写 RestTemplate 代理 + 自研过滤链加固 | Apache APISIX（`jwt-auth` + Casbin 授权插件） | Spring Cloud Gateway 构建于 WebFlux，与本项目 `spring-boot-starter-web`（servlet）**不兼容**（SR-09），官方处置方式是切响应式或移除 web starter，代价过大；APISIX 集成难度 2/5，需额外引入 OpenResty + etcd，与 K1 一键启停目标冲突 |
| 认证与授权 | Spring Security + JWT（对照 `mall-security` 模块划分） | Sa-Token（mall-swarm `master` 分支选型） | B4 `dev-v2` 分支与本项目同为 Spring Boot 2.7，Spring Security 生态成熟且与现有 servlet 过滤链契合；Sa-Token 仅出现在 mall-swarm 已升级的 `master` 分支，引入需额外学习成本且无同栈参照 |
| 服务间身份信任 | HMAC 签名信任链（网关签发，下游 common 拦截器校验） | mTLS / 内部 Token 白名单 | 直接对治 K5「下游直接信任 `X-User-Id`，可直连绕过网关冒充任意用户」；HMAC 在单机 Compose 下零额外组件，mTLS 需证书体系与轮换机制，成本过高。**约束**：ARCH 明确「网关不依赖 common」，签名生成需独立实现 |
| 密钥管理 | `env.sh` 启动时 `openssl rand` 生成并写入 `.env` | HashiCorp Vault（B5 `jwt-auth` 支持的方式） | 呼应 K19 既定方案，单机演示场景零依赖；Vault 为多环境生产级选择，当前引入成本不成比例 |
| 层次化评论存储 | MySQL 8 单表自关联（`parent_id` + `root_id` + `type`）+ 递归 CTE | 闭包表（closure table） | B6 生产验证邻接表 + 递归 CTE 足以支撑嵌套回复；本项目深度固定为 3，闭包表带来的额外关系表与写放大不划算（SR-21）。**关键约束**：查询必须走数据库侧递归，若退化为应用层循环即落入「Naive Trees」反模式（SR-20） |
| 并发控制原语 | P0：服务内本地 `Semaphore`（ARCH §1.4 已选）；演进：Redisson `RPermitExpirableSemaphore` | 令牌桶限流 / 消息队列削峰 | 单机单实例下本地信号量已足够且零依赖；Redisson 版本具备唯一许可 ID 与租约、崩溃自动释放（SR-11），为多实例扩容预留。令牌桶语义是「拒绝」而非「排队」，与诉求③相悖；MQ 已由 K13 决策排除 |
| 排队交互契约 | HTTP 202 + 排队令牌 + 2s 轮询 + 自动继续 | 长轮询 / WebSocket / SSE | 借鉴 B1「请求队列 + 指数退避」与 B2「等待状态独立回传 + 位置稳定 + 自动放行」；轮询实现成本最低且不引入新协议栈。**前置**：必须先改造 `request.js`（K12） |
| Token 生命周期 | JWT + Redis 黑名单（登出即失效） | 不透明 Token + Redis 集中会话 | 沿用现状最小改动。**缺口**：K24 证实 mobile BFF(8089) 独立 `AuthInterceptor` 不读 `X-User-Id` 且无 Redis，黑名单在 BFF 侧不生效，需按 U-01 裁决后补齐 |
| 交付编排 | Docker Compose（单机） | Kubernetes（mall-swarm 提供方案） | B3 官方安装路径即 `docker compose up`，B4 亦以 Docker 为主；单机演示场景下 K8s 的运维与学习成本远超收益，且与 K1「一键启停」目标背离 |
| 前端主题 | Element Plus CSS 变量覆盖 `--el-color-primary` 系列 | Tailwind CSS / SCSS 变量重编译 | K26 已定；避免 Vite4 + Element Plus 主题编译踩坑，且无标杆提供 Vue3 可迁移方案（§3.3 缺口 1） |
| Android 签名 | Gradle `signingConfigs` + release keystore，V2/V3 方案，`apksigner verify --verbose` 纳入验收 | Google Play App Signing | 本项目为本地分发无应用市场渠道；debug keystore 为公开凭据不可用于发布（SR-22）。**P0 建议关闭 minify** 以规避 K8 提示的 R8 keep 规则缺失导致的运行时崩溃 |

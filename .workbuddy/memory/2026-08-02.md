## T03d 错误码语义收尾（完整收口，本日主线）

目标：接口返回**真实 HTTP 状态码**（400/401/403/404/409），仅 code=500 软失败保留 HTTP 200。

### 分四轮完成

**轮1 — 网关补丁验证**
`GatewayConfig.java:93` `factory.setOutputStreaming(false)` 已合入。修复 JDK `HttpURLConnection` 在 401 认证挑战时因流式输出无法重放请求体抛 `HttpRetryException`，被 ProxyService 通用 catch 误判成 503。实跑对照全绿。

**轮2 — 2 条越权返 200 真缺陷（安全测试实跑暴露）**
- `ProductService.updateProduct/deleteProduct`：单参 `BusinessException` → code=500 → HTTP 200。改为 `ErrorCode.FORBIDDEN` / `NOT_FOUND`
- `OrderService.getOrderByIdAndUserId`：一条 SQL 拼 id+归属，越权返 null → `Result.success(null)` → **HTTP 200 + success:true**。拆成 `requireOrder` → 404，再校验归属 → 403
- 顺带：`AddressService.updateAddress`、`OrderService.payOrder/cancelOrder` 归属校验 → 403

**轮3 — 3 处「半迁移」（QA 覆盖度体检发现）**
规律：**同一方法内 403 分支改了、404 分支漏了**，导致同一语义两套口径。
- `payOrder`/`cancelOrder` 的「订单不存在」仍 200+500，而 `GET /order/{id}` 已是 404 → 统一改走 `requireOrder`
- `ProductService.getProductById` 查不存在商品返回 `200 success:true data:null` → 改抛 404
- `AddressService.deleteAddress`/`setDefault` 无存在性校验 → 越权与不存在都报「操作成功」
- **工程师额外挖出数据 bug**：`setDefault` 是「先 `clearDefault(userId)` 后校验」，导致「把别人地址设为默认」这个非法操作会**清掉自己原有的默认地址**再返回成功。已把校验提到 clearDefault 之前

**轮4 — mobile BFF 的 ErrorDecoder（系统性暗伤）**
mobile 模块 Feign **没配 `ErrorDecoder`**，走 `ErrorDecoder.Default` → 非 2xx 一律抛 `FeignException` → 穿透到兜底 handler → **所有下游 4xx 退化成 HTTP 200 +「系统异常，请联系管理员」**。
轮2/轮3 把下游改成真 4xx 后，mobile 里所有 `if (!result.isSuccess())` 优雅降级分支**全部变成死代码**（测试全绿只因不覆盖 mobile 错误路径）。
新增 `DownstreamErrorDecoder`：4xx 解 Result 信封重抛 `BusinessException(code,message)`；5xx 统一收敛 503 + 固定文案（不透下游内部异常，防信息泄露）；非标准/空/非 JSON body 用 HTTP 状态兜底；`decode()` 全包 `catch(Throwable)` 绝不二次抛异常。
不变式：`resolveCode` 只在信封 code 落在合法 4xx 区间时采信，否则回退真实 HTTP 状态 —— 保证「真 4xx 永不降级成 200」。

## ⚠️ 环境陷阱（踩过的坑，务必记住）

### 1. 沙箱回收进程组 —— 最顽固的坑
后台任务结束时会 **kill 整个进程组**，`nohup` / `disown` / `exec java` **全都躲不过**。曾试过「启动后 sleep 25s 让 init 收养」，仍被 SIGKILL（日志停在启动后 1 分钟内、无 shutdown 记录）。

**唯一可靠解**：`scripts/daemonize.py` —— 用 Python `subprocess.Popen(..., start_new_session=True)`（内部调 `setsid()`），让 java 进入**全新 session**，拥有独立 PGID，父进程退出后由 init 收养。已验证跨多个 Bash 调用周期存活。
```bash
set -a && . ./.env && set +a   # 不加载 .env 会报 Could not resolve placeholder 'JWT_SECRET'
python3 scripts/daemonize.py <jar> <port> <logfile> <pidfile>
```

**推论：绝不要让 agent 启动/重启服务** —— agent 任务结束时它起的 java 一起陪葬，反而把健康环境搞坏。给 agent 的指令里必须写死这条，让 agent 只改代码+构建 jar，**重启由主进程做**。

### 2. 服务端口被环境变量劫持
裸 `nohup java -jar &` 会被环境里的 `SERVER_PORT` 宽松绑定劫持到随机端口（实测跑到 52576）。**必须用 `--server.port=8088` 命令行参数钉死**（start.sh 注释里已预判此坑）。

### 3. jar 被覆盖后运行中的 JVM 会崩
`mvn package` 覆盖 jar 后，正在运行的 Spring Boot 进程再懒加载新类会报 `ClassNotFoundException`。构建完必须重启，且 `kill` 可能杀不掉（要 `kill -9`）。判断依据：`lsof -nP -iTCP:<port> -sTCP:LISTEN` 还能看到 java。

### 4. HTTP_PROXY 是「休眠地雷」
本机注入了 `HTTP_PROXY`（端口每次会话不同）。**当前对 localhost 是透传的**（加不加 `--noproxy` 都返回 200），这解释了为什么原 e2e_test.sh 一个 `--noproxy` 都没有却能跑。但它随时会醒 —— 醒来时 curl localhost 会被拦成 502 空 body，让人误判服务宕机。所有验证 curl 一律加 `--noproxy localhost`。

### 5. zsh 把 `?` `*` 当 glob
`grep --include=*.java` 报 `no matches found`，URL 带 `?productId=1` 会被吞。**必须加引号**。

### 6. 跨会话资源回收
服务、Docker 容器、任务板都可能在会话间被清空。恢复：`./start.sh --skip-build --skip-frontend`。

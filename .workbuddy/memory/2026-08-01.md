### 排队机制的典型失败模式（T03b 早期版本）
单线程顺序请求也被 202 拦下 + position 恒定不动 + 带票据重投另发新号
= **许可只进不出（active 集合被幽灵许可占满）**。三条必查路径：
1. `release()` 拿到的 `QueueVerdict` 是否携带可定位 active 成员的标识（`PASS` 若是单例则不带 token，删不掉）
2. 异常/超时/断连时 `finally` 是否仍执行 release
3. ZSet 不会自动过期，必须在 Lua 里按 score 主动清理，否则 TTL 形同虚设

### T03b 排队机制 leader 独立复验结论（8/1 深夜）
- 代码已落地并生效：`queue.enabled=true` / permits=50 / 保护 `POST:/order/create` + `PUT:/product/*/deduct`，jar 构建于 23:44
- **鉴权在排队之前**（ProxyService 第 3 步权限、第 4 步排队守卫）→ 无 token 测排队只会拿到 401，必须带真 token 才测得到排队层
- `QueueVerdict.pass(token)` 已修：有票据时返回独立实例，只有 null/空票据才复用 `PASS` 单例 → 「单例吞票据」根因已消除
- `release()` 在 `ProxyService:129` 的 `finally` 里，覆盖转发成功/失败/抛异常；202 分支提前 return 不 release 也正确（`respond()` 票据为 null）
- 实测：空闲态带 token 连发 10 次 `/order/create` → **10/10 直通零 202**；事后 `ZCARD queue:permits:active = 0` 且 `KEYS queue:*` 全空（Redis 空 ZSet 自动删键，是干净归还的正向证据）
- 结论：四条硬验收中 ①空闲不排队 ②许可归零 已过；③僵尸许可 TTL 清理 ④票据重投走真实执行分支 仍需高并发场景实测

### 登录 503 误报根因（高价值，JDK 经典坑）
`GatewayConfig.java:85` 的 `SimpleClientHttpRequestFactory` 没调 `setOutputStreaming(false)`。
JDK `HttpURLConnection` 只在收到 **401/407 认证挑战**时尝试「带凭据重发请求」，但请求体已流式写出无法重放
→ 抛 `java.net.HttpRetryException: cannot retry due to server authentication, in streaming mode`
→ 落到 `ProxyService.java:204` 的通用 `catch (Exception)` → 被当成下游故障返 503。
- **判定手法**：固定端点、只变下游状态码做对照——400/403/404/200 全正常，**唯独 401 变 503**，即可锁定
- 修法：`factory.setOutputStreaming(false)` 一行。本平台 `MultipartFile` 零命中、无文件上传，缓冲进内存无风险
- 不要用「catch ResourceAccessException 硬编码返 401 用户名或密码错误」的兜底：对 token 过期的 POST 文案是错的
- 附带发现：`hasError()` 恒 false → `RestTemplate` 永不抛 `HttpStatusCodeException`，`ProxyService` 那个 catch 是死代码，4xx 走正常返回路径透传

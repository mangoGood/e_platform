## 1. 业务背景与价值

### 1.1 业务背景

- **当前业务现状（行业 / 产品 / 用户规模）**：e_platform 是一套已上线运行的自建全栈电商演示平台，定位为「自营交易与购后互动主站」。技术形态为 Spring Boot 微服务 5 进程 + Vue3 Web 前台 + Kotlin/Compose 买卖家双 App，单机 Docker Compose 部署，存量测试账号 2 个（buyer1 买家、seller1 卖家）。功能齐但底座不可信：网关鉴权仅停留在「Token 可解析」、客户端可伪造身份头穿透到下游、商品评价无购买校验、一键启动脚本为 0 字节空文件、Android 产物为无签名 APK 无法安装。
- **触发本次需求的事件（新场景 / 痛点修复）**：由存量读码勘察暴露的高危缺陷触发——OWASP API1/API2/API5 级越权（网关伪造头穿透、下游无条件信任 `X-User-Id`、直连绕网关）、评价与交易脱节（任意登录用户可刷评）、交付链路断裂（start.sh 为空、APK 不可装）。用户增量诉求五件事：① 补齐鉴权安全底座；② 新建三级评论体系；③ 建立并发保护（排队而非拒绝）；④ 视觉升级；⑤ 修复一键启停交付链路。
- **本系统在产品矩阵中的位置**：本期不新增业务域，而是把现有平台从「功能演示态」升级为「可信交易 + 可对话 + 可交付」的完整形态；在「浏览 → 交易 → 履约 → 口碑 → 复购」价值主线中承担全部环节，新增「身份与权限中心」「三级评论中心」「并发排队服务」三个本期能力。

### 1.2 行业方案

> 同类功能、痛点的行业标杆系统及解决方案（G2 已通过 `research_report.md` 结论，本表为产品侧摘要）。

| 能力 | 优先借鉴标杆 | 借鉴点（产品可感知） | 不借鉴/自研部分 |
| --- | --- | --- | --- |
| ① 鉴权安全底座 | macrozheng/mall（4.80）、Shopify（3.50） | 权限按「资源 × 动作」成对建模；RBAC 四表组织方式 | 网关不引入 Spring Cloud Gateway（WebFlux 与 servlet 栈不兼容）；签名信任链自研 |
| ② 三级评论体系 | Discourse（4.30）、Shopify（3.50） | 单表自关联 + 数据库侧递归查询承载嵌套回复；评价强绑定订单与买家核验 | 第三层追问（L3）Shopify 平铺方案不覆盖，自研 |

| ⑤ 交付链路 | Saleor（3.20）、macrozheng/mall（4.80） | 「完整电商系统的标准分发形态可以就是容器编排一键起栈」形态正当性 | APK 签名机制平台强制，自研补齐 |

### 1.4 术语清单

| 术语 | 英文 / 缩写 | 含义 |
| --- | --- | --- |
| 角色权限模型 | RBAC | 基于角色的访问控制；本项目建 role / permission / role_permission / user_role 四表，权限码采用「资源:动作」格式 |
| 一级评价 | L1 | 买家购后评价，须绑定已完成订单，一订单一商品一评 |
| 卖家回复 | L2 | 商品归属卖家对 L1 的回复，每条 L1 至多一条有效回复 |
| 第三方追问 | L3 | 任意登录用户对 L1 的追问留言，逻辑单层不嵌套 |
| 访问令牌 / 刷新令牌 | Access Token / Refresh Token | 访问令牌 2 小时、刷新令牌 7 天且不携带角色 |
| 信任链 | HMAC 信任链 | 网关对身份与时间戳签名、下游 common 拦截器校验的「网关签发 + 服务校验」两端分离机制 |
| 排队守卫 | Queue Guard | 下单路径的并发许可 + 等待队列，有许可直通、无许可入队回传位次、队满拒绝 |
| 单实例 | Single Instance | 本期显式前提：单节点 Docker Compose、各服务单实例，不做水平扩容 |
| 底座升级 | N2 / IC-01 | 经中间确认 IC-01 裁决的 Spring Boot 2.7→3.x 升级（含 javax→jakarta 改包 + Spring Security 重写），为 F1~F14 的前置里程碑 |
| 越权测试 | OWASP API Top 10 | 本项目重点闭合 API1（对象级授权失效）/ API2（认证失效）/ API5（功能级授权失效） |

## 5. 用户旅程（UserStory）

> 说明：每条 US 对应 §3 中一个功能项（F1–F14 + N2），按 5.1.1~5.1.7 七段式展开；验收标准（5.1.6）均含正常路径与异常路径，并使用 Given / When / Then 格式。N2 为技术前置里程碑，以「运维/交付」视角叙述其作为承载底座的旅程。

### 5.1 US-1：注册登录获取角色与权限（F1）

#### 5.1.1 业务场景

- **视角**：买家 / 卖家（新注册用户、存量账号）。
- **描述逻辑**：用户在注册页选择买家或卖家身份提交，系统按用户类型自动绑定对应角色与权限码，登录后下发角色与权限清单，前端据此渲染功能入口（而非按 user_type 推断）。存量 buyer1 / seller1 账号在迁移后保留原类型并完成角色绑定，新增 admin 账号绑定 ROLE_ADMIN。

#### 5.1.2 业务流程

- **视角**：用户。
- **流程（Given / When / Then）**：
  - **Given** 用户在注册页选择「买家」并提交手机号/账号与密码；
  - **When** 系统创建用户记录并据 `user_type=1` 写入 `user_role` 绑定 `ROLE_BUYER`；
  - **Then** 登录成功后返回 `roles` 与 `permissions`（含 `product:read` 等 7 项），前端按权限渲染「我的订单 / 去评价」等入口。

#### 5.1.3 UE 原型

- 注册页含「买家 / 卖家」身份单选；登录后右上角用户下拉仅展示当前角色有权限的菜单项；无权限入口不展示（不按 user_type 硬编码）。

#### 5.1.4 业务逻辑

- **视角**：业务系统。
- **流程**：注册请求 → `user` 服务建号 → 据 `user_type` 查角色映射 → 写 `user_role` → JWT 生成时带入 `roles` claim → 启动时 `RbacWarmUpRunner` 将角色→权限写入 Redis（`rbac:role:{code}:perms`）→ 登录返回权限清单。

#### 5.1.5 数据描述

- 核心数据：`role` / `permission` / `role_permission` / `user_role` 四表；JWT payload 含 `roles`；Redis 键 `rbac:role:{code}:perms`、`rbac:user:{userId}:perms`。存量迁移经 `migration-v2.sql`（幂等）完成。

#### 5.1.6 验收标准 AC

- **正常路径**：
  - **Given** 新用户注册选择买家；**When** 提交成功并登录；**Then** 返回 `roles=["ROLE_BUYER"]` 且 `permissions` 含 7 项，`GET /api/user/permissions` 返回一致清单。
- **异常路径**：
  - **Given** 同一账号重复注册；**When** 再次提交；**Then** 返回参数错误（400）且不产生重复 `user_role`。
  - **Given** 新增一个权限码（如 `comment:manage`）；**When** 仅改 migration seed 但未同步改 `RoutePermissionRegistry` 与 `StaticRolePermissions`；**Then** Redis 故障时该权限出现漂移，须三处同步（此条为回归约束，纳入 F14 检查）。
  - **Given** 存量 seller1 登录；**When** 查询权限；**Then** 仍绑定 `ROLE_SELLER` 且原 `user_type` 字段保留向后兼容。

#### 5.1.7 外部集成接口

- 无外部系统依赖；依赖内部 MySQL（四表持久化）与 Redis（权限缓存）。密钥与环境由 F12 的 `env.sh` 注入。

### 5.2 US-2：细粒度接口鉴权与 401/403 严格区分（F2）

#### 5.1.1 业务场景

- **视角**：买家 / 卖家 / 安全合规评审。
- **描述逻辑**：用户调用任一接口时，网关按「路径 + 方法 → 权限码」顺序敏感映射表决策：公开路径放行；未登录访问需登录路径返回 401；已登录但无权限码返回 403；兜底默认需登录（新接口漏登记不会裸奔）。下游服务再做归属校验作为第二道防线。

#### 5.1.2 业务流程

- **Given** 买家持有效 Token 调用 `POST /api/product/add`；
- **When** 网关 `RoutePermissionRegistry` 命中该路径需 `product:write`，而买家仅持 `ROLE_BUYER`；
- **Then** 返回真实 HTTP **403**，响应体含可读原因，前端仅提示不跳转登录。

#### 5.1.3 UE 原型

- 前端统一拦截器：401 执行登出跳转并节流去重；403 仅 `ElMessage.error` 提示不跳转；五类提示样式统一（对齐 V7）。

#### 5.1.4 业务逻辑

- 网关 7 步管线：INTERNAL_DENY 判定 → TokenResolver → RoutePermissionRegistry 决策 → QueueService 守卫 → HeaderSanitizer → GatewaySigner → RestTemplate 转发；兜底 `/**` 为 AUTHENTICATED。归属校验（如「是不是自己的商品」）一律在服务层做，网关只判「有没有门票」。

#### 5.1.5 数据描述

- 路由权限映射表（22 条，顺序敏感）；Redis `rbac:role:{code}:perms` 缓存；权限码来源为 JWT `roles` 经 Redis 读取，miss 时降级静态角色映射。

#### 5.1.6 验收标准 AC

- **正常路径**：
  - **Given** 游客访问 `GET /api/product/list`；**When** 请求到达；**Then** 返回 200 商品列表（公开路径放行）。
  - **Given** 已登录买家访问自己的订单 `GET /api/order/user`；**When** 携带有效 Token；**Then** 返回 200 且仅本人订单。
- **异常路径**：
  - **Given** 无 Token 调用 `POST /api/product/add`；**When** 网关解析失败；**Then** 返回真实 HTTP **401**。
  - **Given** 买家 Token 调用 `POST /api/product/add`；**When** 权限码不足；**Then** 返回真实 HTTP **403**（非 200 + body.code）。
  - **Given** 新增未登记的受保护接口；**When** 匿名访问；**Then** 命中兜底 AUTHENTICATED 返回 401，不裸奔。

#### 5.1.7 外部集成接口

- 依赖 Redis（权限缓存）；与 F1 共用权限数据；与 F4 共用网关安全管线。

### 5.3 US-3：Token 全生命周期与登出即时失效（F3）

#### 5.1.1 业务场景

- **视角**：买家 / 卖家 / 移动端用户。
- **描述逻辑**：登录获取访问令牌（2h）与刷新令牌（7d，不带角色）；登出将当前 Token 的 `jti` 写入 Redis 黑名单（TTL = 剩余有效期）；网关与移动聚合层均校验黑名单，闭合移动端旁路缺口（U-01 已采纳补查黑名单），登出后旧 Token 即使被截获也无法冒用。

#### 5.1.2 业务流程

- **Given** 用户已登录并持有访问令牌；
- **When** 用户点击登出，前端调用 `POST /api/user/logout`；
- **Then** 该 Token 的 `jti` 写入 `auth:blacklist:{jti}`，TTL = 剩余有效期；此后任一请求携此 Token 均返回 401。

#### 5.1.3 UE 原型

- 前端登出后清空本地 Token 与 `queueToken`；移动端登录页可重新登录；登出后旧令牌在 Web 与 App 均立即失效。

#### 5.1.4 业务逻辑

- 登录签发 access/refresh（JWT claims 含 `jti`）；登出接口将 `jti` 写 Redis 黑名单；`TokenResolver` 解析后先查黑名单，命中即 401；移动聚合层（8089）补 redis starter 查黑名单（U-01 方案 a，约 20 行）；刷新接口凭 refreshToken 换新，旧访问令牌仍受黑名单约束。

#### 5.1.5 数据描述

- Redis 键 `auth:blacklist:{jti}`（TTL = Token 剩余有效期）；JWT claims：`jti/sub/userId/roles/typ`，refresh `typ=refresh` 不带 roles。

#### 5.1.6 验收标准 AC

- **正常路径**：
  - **Given** 用户登录后持有效访问令牌；**When** 调用需登录接口；**Then** 返回 200 业务结果。
  - **Given** 访问令牌 2h 临近过期；**When** 调用 `POST /api/user/refresh` 凭 refreshToken；**Then** 返回新 accessToken（不含角色变更提权）。
- **异常路径**：
  - **Given** 用户登出后持旧访问令牌；**When** 调用受保护接口；**Then** 黑名单命中返回真实 HTTP **401**。
  - **Given** 移动端用户登出；**When** 持旧 Token 直连移动聚合层；**Then** 同样返回 401（BFF 侧黑名单生效）。
  - **Given** 登出后超过令牌剩余有效期；**When** 黑名单 TTL 过期；**Then** 键自动清理，无残留。

#### 5.1.7 外部集成接口

- 依赖 Redis（黑名单）；与 F1 的 JWT 工具共用；移动聚合层经内部 Feign/AuthInterceptor 复用黑名单口径。

### 5.4 US-4：身份头净化与签名信任链（F4）

#### 5.1.1 业务场景

- **视角**：安全合规评审 / 下游服务。
- **描述逻辑**：网关在转发前按前缀黑名单（含 `x-user-`、`x-gateway-`、`x-internal-`）剥离客户端传入的全部内部身份头，身份头只能由网关写入；网关对 `userId+userType+roles+timestamp` 做 HMAC 签名，下游统一拦截器校验（5 分钟窗口、常量时间比较）；匿名请求同样签名以防「无签名即匿名」绕过；直连下游端口无签名返回 401。

#### 5.1.2 业务流程

- **Given** 攻击者携带伪造 `X-User-Id: 2` 与有效用户 A 的 Token 调用 `PUT /api/product/9`；
- **When** 网关 `HeaderSanitizer` 先剥离伪造头，再由 `GatewaySigner` 用网关身份写入签名头；
- **Then** 下游 `GatewaySignatureInterceptor` 验签通过，但服务层归属校验发现「不是自己的商品」返回 403；直连 8086 无签名则返回 401。

#### 5.1.3 UE 原型

- （无前端交互界面；为系统间横切能力）运维/安全可通过 `tests/security_test.sh` 查看决策日志与拦截结果。

#### 5.1.4 业务逻辑

- 网关 7 步管线第 ⑤⑥步：`HeaderSanitizer` 基于前缀黑名单剥离（默认拒绝，防未来新增头绕过）→ `GatewaySigner` 写 `X-User-Id/X-User-Type/X-User-Roles/X-Gateway-Ts/X-Gateway-Sign`；下游 common 拦截器 `MessageDigest.isEqual` 常量时间比较，超窗 401；匿名 userId/userType 为 `"0"`、roles 空串。

#### 5.1.5 数据描述

- 签名原文字段顺序固定：`userId\nuserType\nroles\ntimestamp`（HmacSHA256 + Base64 URL-safe 无填充）；密钥 `GATEWAY_SIGN_SECRET`（环境变量，由 `env.sh` 随机生成）；`X-Internal-Token` 白名单用于 order→product 服务间直连。

#### 5.1.6 验收标准 AC

- **正常路径**：
  - **Given** 合法用户 A 持 Token 调用受保护接口；**When** 网关签名、下游验签通过且归属校验通过；**Then** 返回 200 业务结果，下游看到的 `X-User-Id` 为 A。
- **异常路径**：
  - **Given** 携带用户 A Token + 伪造 `X-User-Id: B`；**When** 到达下游；**Then** 下游看到的身份为 A（伪造头已被剥离），归属校验基于 A。
  - **Given** 直连 `localhost:8086` 伪造 `X-User-Id` 调写接口；**When** 无网关签名；**Then** 返回真实 HTTP **401**。
  - **Given** 签名时间戳超过 5 分钟；**When** 下游校验；**Then** 返回 401（重放窗口外）。
  - **Given** 匿名请求；**When** 网关同样签名后转发；**Then** 下游以匿名身份处理，不出现「无签名即匿名」绕过。

#### 5.1.7 外部集成接口

- 依赖环境变量 `GATEWAY_SIGN_SECRET`（由 F12 `env.sh` 生成注入）；common 模块 `GatewaySignatureInterceptor` 校验；网关不依赖 common（代码分离，避免自我拦截）。

### 5.5 US-5：三级评论模型与树形查询（F5）

#### 5.1.1 业务场景

- **视角**：游客 / 买家 / 卖家。
- **描述逻辑**：用户在商品详情页查看评论区，系统返回树形结构（L1 倒序、L2 紧随、L3 正序），附评分概览（平均分 + 星级分布）与可视上下文（前端动态显隐与置灰原因的唯一数据来源）；父级不可见时其下级级联过滤；用户名脱敏展示；游客可读全部三层。

#### 5.1.2 业务流程

- **Given** 游客访问 `GET /api/comment/product/{productId}`；
- **When** 系统按 `root_id` 单次批量查询（数据库侧递归，禁止应用层逐层循环）；
- **Then** 返回树形评论 + `summary`(ratingAvg/ratingCount/distribution) + `viewerContext`（置灰原因），游客可见全部三层，用户名脱敏。

#### 5.1.3 UE 原型

- 商品详情页评论区：L1 主卡（头像 + 脱敏名 + 星级 + 内容）；L2 缩进 24px 浅橙底 + 「卖家」徽标；L3 再缩进浅灰底对话流高亮 @昵称；骨架屏占位。

#### 5.1.4 业务逻辑

- `Comment` 实体单表自关联（`parent_id`/`root_id`/`type`）；查询走基于 `root_id` 的批量查询或 MySQL 8 递归 CTE；级联可见性在查询层 JOIN 回 L1 过滤（L1 逻辑删除则其 L2/L3 不返回）；`MaskUtil.maskUsername` 脱敏；`UserClient` Feign 批量取用户名避免 N+1。

#### 5.1.5 数据描述

- `comment` 表（与旧 `Review` 共表）：`parent_id`(默认0)/`root_id`(默认0)/`type`(1评价/2回复/3追问)/`reply_to_user_id`/`seller_id`/`reply_count`；索引 `idx_root_id`/`idx_parent_id`；评分聚合 `rating_avg`/`rating_count`（同事务刷新 + 定时兜底）。

#### 5.1.6 验收标准 AC

- **正常路径**：
  - **Given** 商品有 3 条 L1，各含 L2 与若干 L3；**When** 游客查询；**Then** 返回树形，L1 倒序、L2 紧随、L3 正序，附评分概览，用户名脱敏。
  - **Given** 买家已购；**When** 查询得到 `viewerContext.canReview=true`；**Then** 前端「去评价」入口可点击。
- **异常路径**：
  - **Given** 某 L1 被逻辑删除/隐藏；**When** 查询该商品评论；**Then** 其下 L2/L3 级联不返回。
  - **Given** 前端尝试通过 `parent_id` 构造第 4 层；**When** 服务端赋值（永不信任前端）；**Then** DB 不产生第 4 层，L3 的 `parent_id=root_id=L1.id`。

#### 5.1.7 外部集成接口

- 依赖交易中心 `GET /order/internal/purchased`（内部接口，INTERNAL_DENY，用于购买校验，见 US-6）；依赖身份与权限中心 `GET /user/internal/batch`（批量用户名脱敏）；两者均经 Feign + 内部令牌。

### 5.6 US-6：L1 买家购后评价（F6）

#### 5.1.6 验收标准 AC

#### 5.1.7 外部集成接口

### 5.9 US-9：下单并发排队与降级（F9）

#### 5.1.1 业务场景

- **视角**：买家（高峰期下单）。
- **描述逻辑**：下单路径进入并发许可 + 等待队列守卫：有许可直通、无许可入队回传位次与预计等待、队满拒绝并给友好文案、等待超时自动释放；许可具备持有超时防名额泄漏；Redis 故障时降级为本地信号量并最终直接放行，业务不中断；库存扣减在商品服务内部叠加本地信号量防连接池被打穿。

#### 5.1.2 业务流程

- **Given** 演示 `QUEUE_PERMITS=1` 时买家发起下单；
- **When** 无空闲许可；
- **Then** 返回 202 + `{queueToken, position, estimatedWaitSeconds, totalInQueue}`，前端弹排队遮罩；轮到返回 200 自动继续；队满返回 503。

#### 5.1.3 UE 原型

- 排队遮罩（全局浮层）：展示「前方还有 N 人，预计 X 秒」；遮罩点击无效只能主动放弃；等待超 20s 追加安抚文案；轮到自动继续；刷新可凭 token 恢复。

#### 5.1.4 业务逻辑

- 网关 `QueueService`：Lua 脚本 `queue_acquire`（清理泄漏 → 查去重 → 有空位 GRANTED → 队满 FULL → 否则 QUEUED 返回 ZRANK+1）；`queue_poll`（超时 TIMEOUT / 晋级 GRANTED / WAITING）；`queue_release`。保护点：下单在网关侧排队；库存扣减在商品服务内部本地信号量。`estimatedWaitSeconds = ceil(position/permits) × avgCostMs / 1000`。

#### 5.1.5 数据描述

- Redis ZSet `queue:permits:active` / `queue:waiting`；Hash `queue:token:{token}`（status/userId/bizKey/minPosition）；String `queue:dedup:{userId}:{bizKey}`；List `queue:stats:cost`（滑窗均值，冷启动 500ms）。防超卖真相来源为 `UPDATE product SET stock=stock-qty WHERE id=? AND stock>=qty`（受影响行数 0 即回滚）。

#### 5.1.6 验收标准 AC

- **正常路径**：
  - **Given** 有空闲许可时买家下单；**When** `QueueService.acquire()` 返回 GRANTED；**Then** 直接转发下单，用户无感知。
  - **Given** 50 并发下单；**When** 压测执行；**Then** 超卖 = 0 件、5xx = 0 次、位次可见且只减不增。
- **异常路径**：
  - **Given** 队列已满；**When** 新请求入队；**Then** 返回 503 + 友好文案「当前抢购人数过多，请稍后再试」。
  - **Given** 等待超过 60s（wait-timeout）；**When** `queue_poll` 判定超时；**Then** 返回 408 自动释放名额，不占用。
  - **Given** Redis 不可用；**When** 捕获 `RedisConnectionFailureException`；**Then** 降级 `LocalSemaphoreFallback` 直接放行并告警，下单不中断（排队是体验优化不是正确性保障）。

#### 5.1.7 外部集成接口

- 依赖 Redis（许可/队列/统计）；与交易中心下单接口、商品中心库存扣减接口协同；降级依赖本地信号量（无外部）。

### 5.10 US-10：排队前端体验（F10）

#### 5.1.1 业务场景

- **视角**：买家（Web 前台）。
- **描述逻辑**：前端统一请求层放行全部状态码（不得只放行 2xx）；收到 202 入队响应弹出不可误关的遮罩，展示位次与预计等待且只减不增；每 2s 轮询刷新；轮到后自动重放原请求，业务代码无感知；提供放弃排队；刷新页面可凭 token 恢复排队态。

#### 5.1.2 业务流程

- **Given** 前端首次 `POST /api/order/create` 收到 202；
- **When** `useQueue()` 打开遮罩并每 2s 轮询 `GET /api/queue/status`；
- **Then** 轮到返回 200 时自动用 `X-Queue-Token` 重放原请求，把最终结果 resolve 给原调用方，业务代码无感知。

#### 5.1.3 UE 原型

- `request.js` 改为 `validateStatus: () => true`；202 → `useQueue()`；401 登出跳转节流；403 仅提示；408 提示重新提交；409 抛给调用方切编辑态；429 提示稍后再试；503 提示稍后再试可重试。

#### 5.1.4 业务逻辑

- 拦截器按 HTTP 状态码优先分发；`queueToken` 存 sessionStorage（key `queue:token`）；位次展示取历史最小值实现「只减不增」；`restore()` 页面刷新恢复遮罩。

#### 5.1.5 数据描述

- 前端状态：`queueToken`（sessionStorage）、`minPosition`（历史最小位次）；后端 `queue:token:{token}` 票据；轮询接口 `GET /api/queue/status?token=`。

#### 5.1.6 验收标准 AC

- **正常路径**：
  - **Given** 下单返回 202；**When** 前端弹遮罩并轮询；**Then** 轮到自动继续原请求，订单创建成功，用户无额外点击。
- **异常路径**：
  - **Given** 用户点击遮罩层；**When** 尝试关闭；**Then** 遮罩不关闭（点击层无效），仅「放弃排队」按钮可退出。
  - **Given** 真实位次波动；**When** 展示值计算；**Then** 取历史最小值，不出现「越排越后」。
  - **Given** 用户刷新页面；**When** `restore()` 读取 sessionStorage token；**Then** 恢复排队遮罩与位次，不丢名额。
  - **Given** 用户点「放弃排队」；**When** 调 `POST /api/queue/abandon`；**Then** 释放名额，不产生订单。

#### 5.1.7 外部集成接口

- 依赖网关排队接口（F9 同套契约）；与 F9 共用 `queueToken` 协议。

## 6. 非功能性需求

### 6.1 易用性需求

- **操作便利性**：排队遮罩从收到入队响应到呈现不超过 1 帧渲染周期；评论发表路径不超过 3 步；无权限时入口**置灰并给原因**（禁止隐藏），降低困惑（对齐 V3 零漏判）。
- **UI 一致性**：三个核心页面组件库默认主色残留 0 处；过渡时长统一 200–300ms 且不超过 400ms；开启系统减弱动效偏好时禁用非必要动效（对齐 V8）。
- **引导提示**：全局错误提示 401 触发登出跳转并节流去重、403 仅提示不跳转、408 提示重新提交、409 切换编辑态、503 提示稍后再试；五类提示样式统一（对齐 V7）。
- **错误反馈**：排队等待超 20s 追加安抚文案「正在为你保留名额，请勿关闭页面」；位次展示取历史最小值，严禁「越排越后」。
- **无障碍支持**：尊重 `prefers-reduced-motion`；评论区用户名脱敏展示（`张*三`）；表单必填与长度校验实时提示。

### 6.3 操作与环境需求

- **浏览器兼容性**：Web 前台目标 Chrome / Edge / Firefox 最新两个大版本；桌面（宽度大于 1024px）优先保障，平板（768–1024px）不塌陷，移动（宽度小于 768px）为完整版 F19 范围。

### 6.4 安全性需求

#### 6.4.1 安全密码设置

- 账号密码注册须达到强度：**8 位以上、含大小写字母 + 数字 + 特殊字符**；密码经 BCrypt 加密存储，禁止明文或弱哈希。
- 测试账号（buyer1 / seller1 / admin）密码 123456 仅用于演示，交付文档须明确标注为演示账号、建议验收后修改。

#### 6.4.2 安全软件架构

- 各模块通信安全：网关到下游的身份头只能由网关写入（前缀黑名单剥离客户端伪造头）；网关对身份与时间戳 HMAC 签名，下游统一拦截器校验（5 分钟窗口、常量时间比较）；匿名请求同样签名以防绕过。
- 组件 / 用户 / 资源的认证与访问控制：RBAC 四表 + 「资源:动作」权限码；网关判「有没有门票」、服务层判「是不是自己的资源」两段式；内部接口（deduct/restore、/internal/**）外部访问一律 403（INTERNAL_DENY）。
- 与外系统接口安全：本期无外部业务系统依赖；仅依赖自建 MySQL/Redis；限制未经许可的接口访问，使用适当加密与认证手段（HMAC 签名 + 内部令牌）；网关不依赖 common 避免自我拦截。

#### 6.4.3 安全设计

- 提供认证授权功能：JWT 访问/刷新令牌 + Redis 黑名单登出失效；网关与移动聚合层均校验黑名单（闭合移动端旁路缺口，U-01 已采纳补查黑名单）；未登录 401、无权限 403 严格区分。

#### 6.4.4 安全开发

- 函数入口参数合法性与准确性检查：统一响应体 `{code,message,data,success}`，抛错一律 `throw new BusinessException(ErrorCode.x,"文案")`，禁止 `return Result.error(403,...)`（HTTP 仍 200）。
- 输入边界检查：评论内容长度 L1[5,1000]/L2[1,500]/L3[1,200]；评分 1–5；`parent_id/root_id` 一律服务端赋值永不信任前端。
- 高危漏洞防范：避免可直接利用的高危漏洞；输入输出模块适当过滤（评论内容转义、敏感词过滤为完整版 F17）；禁止未经授权和验证的代码；不存在可绕行安全机制的行为或遗留后门。

#### 6.4.5 安全测试和部署

- 安全扫描测试：`tests/security_test.sh` 12 项越权场景断言（基于真实 HTTP 状态码），纳入交付可重复执行。
- 安全配置基线检查：迁移脚本幂等、密钥随机生成不硬编码、APK 签名校验通过。
- 安全功能测试：越权与并发用例集（F14）覆盖伪造头/跨用户/未购/登出复用/直连绕网关等。
- 上线前不存在高危风险：12/12 越权场景拦截通过、50 并发零超卖零 5xx 后方可视为无已知高危越权风险上线。

#### 6.4.6 数据安全

- **数据存储和传输加密**：用户密码经 BCrypt 加密存储；身份鉴别信息（JWT）经网关 HMAC 签名防篡改；内部令牌 `INTERNAL_TOKEN` 用于服务间调用；密钥（JWT_SECRET / GATEWAY_SIGN_SECRET / INTERNAL_TOKEN）经环境变量注入，传输过程不落明文配置；Redis 黑名单与权限缓存不含明文密码。

- **候选方案**：
  - **方案 A（演示级建议值冻结）**：采用本文 §6.2 表中给出的演示级建议值（登录 P50≤300ms / P90≤800ms / P99≤1.5s；商品 GET P50≤200ms；下单 P50≤500ms；下单峰值 QPS≈50；商品数百/评价数千/用户十余）。优点：文档即可完整冻结，下游 system-architect 有数值可循。缺点：非真实压测得出，可能与单机演示环境实际表现有偏差；与高层「不承诺量化可用性等级」口径存在张力。
  - **方案 B（仅沿用已冻结基线，时延/吞吐留待下游标定）**：§6.2 只保留高层已冻结基线（50 并发零超卖零 5xx、错误语义一致 100%、迁移幂等 3 次），P50/P90/P99、QPS/TPS、数据规模上限不写具体数字，由 system-architect 在《系统设计》中按单机演示环境标定后回填。优点：不制造隐性 SLA，与高层口径一致。缺点：§6.2 暂不出现具体百分位数。

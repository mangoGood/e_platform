## 修复清单

### 轮 1 — 网关 503 误判（已合入验证）

`GatewayConfig.java:93` 加 `factory.setOutputStreaming(false)`。

JDK `HttpURLConnection` 在 401 认证挑战时因流式输出无法重放请求体，抛 `HttpRetryException`，被 ProxyService 的通用 catch 误判成 503。关掉流式输出后，401 能正确透传。

### 轮 2 — 2 条越权返 200（安全测试实跑暴露）

| 缺陷 | 现象 | 修复 |
|---|---|---|
| `ProductService.updateProduct` / `deleteProduct` | 越权改价/删商品 → `HTTP 200 {"code":500,"message":"无权限修改该商品"}` | 单参 `BusinessException` → `ErrorCode.FORBIDDEN` / `NOT_FOUND` |
| `OrderService.getOrderByIdAndUserId` | 查他人订单 → `HTTP 200 {"code":200,"data":null,"success":true}` | 一条 SQL 拆两步：`requireOrder` → 404，再校验归属 → 403 |

第二条尤其糟糕：**越权访问被标记为 `success:true`**。

### 轮 3 — 3 处「半迁移」（QA 覆盖度体检发现）

规律性问题：**同一方法内 403 分支改了、404 分支漏了**，同一业务语义出现两套口径。

| 缺陷 | 现象 |
|---|---|
| `payOrder` / `cancelOrder` | 「订单不存在」仍 `200+500`，而 `GET /order/{id}` 已是 404 |
| `getProductById` | 查不存在商品 → `200 success:true data:null`，客户端无法区分「不存在」和「字段为空」 |
| `deleteAddress` / `setDefault` | 无存在性校验，越权与不存在都报「操作成功」 |

**工程师额外挖出一个数据 bug**（QA 未报）：`setDefault` 是「先 `clearDefault(userId)` 后校验」——
> 「把别人的地址设为默认」这个非法操作，会成功清掉**你自己**原有的默认地址，然后告诉你「操作成功」。用户下次下单会发现默认地址凭空消失。

已把校验提到 `clearDefault` 之前，字节码验证顺序正确（403 `athrow` 在 offset 32，`clearDefault` 在 35）。

### 轮 4 — mobile BFF 的 ErrorDecoder（系统性暗伤）

**根因**：mobile 模块 Feign 未配置 `ErrorDecoder`，走 `ErrorDecoder.Default` —— 非 2xx 一律抛 `FeignException`，穿透到兜底 handler。

**后果**：轮 2/3 把下游改成真 4xx 之后，mobile 里所有 `if (!result.isSuccess())` 优雅降级分支**全部变成死代码**：

```
GET    /api/mobile/products/999999   → HTTP 200 「系统异常，请联系管理员」
POST   /api/mobile/orders/999999/pay → HTTP 200 「系统异常，请联系管理员」
DELETE /api/mobile/addresses/999999  → HTTP 200 「系统异常，请联系管理员」
```

比改造前更糟——改造前至少文案是准的。测试全绿只是因为**不覆盖 mobile 错误路径**。

**修复**：新增 `DownstreamErrorDecoder`

| 下游响应 | 处理 | 理由 |
|---|---|---|
| 4xx + 标准 Result 信封 | 解封重抛 `BusinessException(code, message)` | 逐字还原下游文案，与直连口径一致 |
| 4xx + 非标准/空/非 JSON body | 用 HTTP 状态兜底 | 解不出信封也不能丢语义 |
| 4xx 但信封 code 是 5xx/缺失/非数字 | 以真实 HTTP 状态为准 | 守住「4xx 绝不降级成 200」 |
| 5xx | 统一收敛 503 + 固定文案 | 区分「下游挂了」与「业务拒绝」；不透下游内部异常，防信息泄露 |
| 401 / 403 | 逐字透传，日志提示 `internal.token mismatch` | 保留鉴权语义，便于定位令牌问题 |

`decode()` 全包 `catch(Throwable)`，**任何解析失败都降级 503，绝不二次抛异常**。

**装配证据**（不是「我写了个 Bean」，是「我验证了它被装配」）：
- `javap` 确认 `@Configuration` + `@Bean` 双标记齐全
- 反射测试从真实 Feign 代理沿 `FeignInvocationHandler → SynchronousMethodHandler → AsyncResponseHandler → errorDecoder` 抠出实例，断言三个 client 共享同一个 `DownstreamErrorDecoder`、`dismiss404 == false`
- **负向对照**：临时注掉 `@Bean` 重跑，6 个断言中 5 个失败并报「实际装配的是 `ErrorDecoder$Default`」——证明测试真能抓到未装配，而非恒真

单测 26/26（20 解码 + 6 装配）。

## 环境问题：沙箱回收进程组

本轮最大的非功能障碍。后台任务结束时会 kill 整个进程组，`nohup` / `disown` / `exec java` **全都躲不过**（试过「启动后 sleep 25s 让 init 收养」，仍被 SIGKILL）。

**解法**：`scripts/daemonize.py` 用 Python `subprocess.Popen(..., start_new_session=True)`（内部调 `setsid()`），让 java 进入全新 session、拥有独立 PGID，父进程退出后由 init 收养。已验证跨多个调用周期存活。

```bash
set -a && . ./.env && set +a          # 不加载 .env 会报 JWT_SECRET 未解析
python3 scripts/daemonize.py <jar> <port> <logfile> <pidfile>
```

**衍生纪律**：绝不让 agent 启动/重启服务——agent 任务结束时它起的 java 一起陪葬。本轮所有 agent 指令都写死「只改代码 + 构建 jar，重启由主进程做」。
